## 二、问题清单(基于源码证据)

### P0-1 Oracle / Elasticsearch 是"空壳"引擎 ✅ 已实现(2026-08-06)

> 实施结果:能力矩阵移除这两类引擎;新建连接对话框中变为"规划中,暂不支持"的禁用选项;存量 Oracle/Elasticsearch 连接调用打开/执行/读表等入口时,由注册表门禁返回明确错误("暂不支持 X 引擎"),不再伪造成功,也不再触碰 MySQL 驱动。

**现状:**

- UI 可选:`ConnectionDialog.tsx` 提供 Oracle(默认端口 1521)与 Elasticsearch(默认端口 9200)选项。
- 能力声明存在:`shared/engine-capabilities.ts` 为两者声明了对象类型与引号规则。
- **没有任何适配器实现**:`src/main/services/adapters/` 下 10 个适配器文件,Oracle / Elasticsearch 命中数为 0。
- `ConnectionService.open()`(connection-service.ts:707)调用 `readDatabases()`(connection-service.ts:1809),该函数对这两种引擎落入通用 fallback(connection-service.ts:1831),**不做真实连接**,直接伪造一个名为 `defaultDatabase || 'default'` 的空数据库返回,导致"打开成功"的假象。
- `executeQuery()`(connection-service.ts:863)没有 Oracle / Elasticsearch 分支,SQL 最终落到 `dbWorkerMysqlQuery`(connection-service.ts:976),用 **MySQL 驱动**连接 1521/9200 端口,必然报错。

**影响:** 宣称支持 14 种引擎,实际可用的数据库引擎为 12 种 + SSH;Oracle / Elasticsearch 连接可保存、可"打开",但一执行就失败,属于误导性产品状态。

**方案(二选一,建议先做决策):**

1. **短期收敛(推荐):** 从连接对话框与能力矩阵中移除这两种引擎;存量连接在打开时给出明确提示;README 口径改为"当前支持 12 种数据库引擎 + SSH"。
2. **长期补实现:** Oracle 使用 `oracledb`(原生依赖,打包需 node-gyp rebuild + 三平台验证),元数据走 `ALL_TABLES` / `ALL_TAB_COLUMNS` 等视图;Elasticsearch 使用 HTTP `_sql` 接口或 DSL 翻译,元数据走 `_cat` / `_mapping`。按需排期,建议排在收敛之后。

### P0-2 引擎分派是 if/else 链 + MySQL 兜底,未知引擎会静默走错驱动 ✅ 已实现(2026-08-06)

> 实施结果:新增 `src/main/services/engine-registry.ts`(12 个引擎注册表 + `requireEngineEntry` 门禁 + 全引擎健康检查)。`readDatabases / executeQuery / fetchMoreRows / readTableData / getTableDefinition / updateQueryRow / deleteQueryRow / executeSql / listCharsets / closeRuntimeResources / readDatabaseDetail` 全部改为注册表路由,MySQL 家族实现下沉到注册表,`executeQuery` 等入口不再有引擎 if/else 分派,未知引擎不会落到 MySQL worker。

**现状:** `open / close / readDatabases / executeQuery / readTableData / processList` 等入口各自维护一段引擎 if/else;漏配引擎时不会报"不支持",而是静默回退——最危险的是 `executeQuery()` 对未知引擎直接走 MySQL worker(connection-service.ts:976)。

**方案:** 建立**引擎注册表 + 统一适配器接口**,以注册表为唯一事实源:

```ts
interface EngineAdapter {
  engineId: EngineId
  open(connection): Promise<void>
  close(connection): Promise<void>
  isHealthy(connection): Promise<boolean>
  readDatabases(connection, options): Promise<DatabaseItem[]>
  readTableData(connection, input): Promise<TableDataResult>
  execute(connection, databaseName, sql): Promise<QueryExecutionResult>
  fetchMore(connection, cursor): Promise<CursorPage>
  getTableDefinition(connection, input): Promise<TableDefinitionResult>
  updateRow / deleteRow / exportSql / ...
}

const engineRegistry: Record<EngineId, EngineAdapter> = {
  mysql: mysqlAdapter, mariadb: mysqlAdapter, tidb: mysqlAdapter,
  postgresql: postgresqlAdapter, kingbase: kingbaseAdapter, dm: dmAdapter,
  'sql server': mssqlAdapter, sqlite: sqliteAdapter, duckdb: duckdbAdapter,
  clickhouse: clickhouseAdapter, mongodb: mongodbAdapter, redis: redisAdapter,
}
```

- `ConnectionService` 只做路由:查注册表 → 取适配器 → 调用;未注册引擎在 `open` / `execute` 前就返回明确错误,禁止回退。
- 同一家族引擎(MySQL/MariaDB/TiDB、PG 系/金仓/达梦)通过"适配器实例 + 能力配置"复用,而不是复制 if/else。
- `shared/engine-capabilities.ts` 改为从注册表派生(或与注册表做一致性校验),避免能力声明与实现脱节。

### P0-3 心跳保活只覆盖 MySQL 家族 ✅ 已实现(2026-08-06)

> 实施结果:注册表为每个引擎提供 `healthCheck`(MySQL 家族 `SELECT 1`、PG 系 `SELECT 1`、SQLite/DuckDB `SELECT 1`、SQL Server `SELECT 1`、MongoDB 轻量列库、ClickHouse `SELECT 1`、Redis `PING`),心跳定时器遍历全部已打开连接调用对应健康检查。

**现状:** `performHeartbeat()`(connection-service.ts:480)只对 MySQL/MariaDB/TiDB 执行 `SELECT 1`;PostgreSQL、SQL Server、MongoDB、ClickHouse、Redis 打开后无保活,长连接可能被服务端或 NAT 断开而 UI 无感知。

**方案:** 适配器接口增加 `isHealthy()`,心跳统一遍历已打开连接并调用对应适配器;心跳失败只告警并标记连接状态,不自动断开。

## 五、风险与对策

| 风险 | 对策 |
|---|---|
| 注册表重构是横向改动,易引入回归 | 分引擎逐个迁移,每步 `typecheck + build`;IPC 协议保持不变;先迁移只读路径(open/readDatabases),再迁移写路径 |
| Oracle 若补实现,`oracledb` 原生依赖在 Electron 打包存在 ABI 风险 | 收敛优先;补实现时独立分支验证三平台打包,不进主线 |
| repository 拆分影响本地数据 | 保留 `schema_version` 迁移框架,拆表不改表结构;先拆分纯读表,写表后置 |
| 心跳扩展对远程库增加负载 | 心跳频率可配置(默认 45s 可调),只对已打开连接执行轻量查询 |
